## Executive summary

23 risks logged. **3 CRITICAL, 9 HIGH, 8 MEDIUM, 3 LOW.** The single most urgent is **R-05** — emotionally-charged inputs ("i feel sad") that fall outside the deterministic crisis keyword set get dropped onto the QC degraded-quality fallback path with **no usable response and no second-line crisis re-check that the user can see**, leaving a vulnerable user empty-handed. Second most urgent is **R-04 / R-12** — the prompt-assembler in [src/coaching/orchestrator.ts:232](src/coaching/orchestrator.ts#L232) is called **outside any try/catch**, so every `PromptAssemblyError` (E5–E9) bubbles unhandled out of `runCoachingTurn`, lands in the queue-processor dead-letter handler, and the user sees no response at all (this is the most-likely root cause of Bug 4's silent failures across 6 retries). Posture: **NEEDS-ATTENTION** — the system is not unsafe to run, but the screenshot bugs prove production-realistic inputs hit observable degradation, and several controls (latency cap, audit-log fail-closed coverage, sponsor 30-floor integration test, Tier-B crisis classifier) are documentation-only or partial. Phase A is gated on closing R-01 through R-05 and at least the HIGH items in R-06 through R-13. The remaining MEDIUMs and LOWs are batched-able cleanups.

## Severity legend

- **CRITICAL** — user safety, data loss, or full pipeline outage. Must fix before any further launch milestone.
- **HIGH** — affects every user / large user fraction; visible degradation; PRD hard-floor at risk.
- **MEDIUM** — affects some users, recoverable, observable.
- **LOW** — defensive depth, future-proofing, cleanup.

## Cross-cutting observations

**Fallback chains terminate without trace emission in 3 places.** R-15, R-16, and parts of R-14 share a pattern: when a downstream module (`whatsapp-delivery`, `quality-check`) returns a structured result instead of throwing, the trace ends up with a string-y `reason` field rather than a structured `endEvent`. An auditor reading just the trace cannot reconstruct *which* downstream end-event caused the upstream `E11_ServiceUnavailable`. This is a small, repeated wiring miss — adding one or two structured fields to `TurnTrace` would resolve all three.

**Three production-impacting bugs (R-01, R-02, R-04) all stem from missing structural guards in `coaching/orchestrator.ts`.** The orchestrator is structured as a clean BPMN-like sequence, but it lacks (a) a session-state guard before short-circuit branches and (b) a try/catch around `assemblePrompt`. R-04 specifically is the highest-impact single fix in this audit — it's likely the cause of multiple "no response" incidents in the screenshot, and the fix is one try block. R-01 and R-02 share a fix surface (intent disambiguation + session-state guard).

**Documentation-only invariants are common, particularly around budget enforcement.** R-06 (latency budget), R-07 (regen timeout), R-08 (key rotation), R-19 (E10 deferred) are all "documented in a comment, not enforced or asserted." This is a recurring pattern that scales linearly with code growth — the next refactor will softly relax one of these without tripping any test.

**Crisis-path coverage has a deterministic gap at the emotional-distress border.** R-05 and R-13 are in the same vicinity: the deterministic fast-path is conservative, and Tier-B handling is fully LLM-dependent with no CI exercise. The combination means a class of "vulnerable but non-keyword" inputs is treated by an unverified path. This is the audit's CRITICAL cluster, and it is the work that should gate the next launch.

**PII discipline is genuinely tight.** Every `hashPhone` call site is clean, the LLM prompt-assembly explicitly omits `firstName` ([blocks.ts:56–60](src/prompt-assembly/blocks.ts#L56-L60)), traces use `userIdHash` not `phoneE164`, and the audit-log fail-closed contract is hard-throw with explicit test coverage. No PII rows fired during the audit; the discipline is an asset.

**Sponsor 30-floor enforcement is layered correctly but minimally tested.** The helper is invoked at every aggregation site, but only the helper itself has unit tests (R-09). One integration test would close the gap.
