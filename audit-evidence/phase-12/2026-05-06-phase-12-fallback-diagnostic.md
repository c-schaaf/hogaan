## TL;DR

Three findings:

1. **Library promotion never landed in DB.** `audit-evidence/phase-12/SUMMARY.md`
   reports `voice_rules v2` and `cultural_framing v2` "promoted to active".
   Neither row exists in the production `library_versions` table. The
   Phase-12-ratified content lives only in the seed files
   ([src/libraries/seed/voice-rules.ts](../../src/libraries/seed/voice-rules.ts),
   [src/libraries/seed/cultural-framing.ts](../../src/libraries/seed/cultural-framing.ts)).
   Active DB rows are the pre-Phase-12 hashes published 2026-05-04 at
   seed time. **Result:** prompt assembly resolves OLD content from DB
   while voice-consistency scores against the NEW seed centroid —
   guaranteed mismatch on every turn that runs voice-consistency.

2. **Reported "~50% fallback rate" not present in `turns` table.** The
   last 200 rows in the table show 1× E3, 1× E6, and 198× E1/E2 (1%
   fallback). Of 100 most-recent rows pulled, only 5 are real coaching
   turns; 95 are seed/synthetic fixtures with `responseText="synthetic
   response"` (length 18) and empty `degradationFlags={}`. The user's
   premise needs a source check — are T1/T4/T7/T8 from a synthetic test
   harness, not production?

3. **Per-check failure detail is not persisted.** `qc.checks[]` and
   `qc.correctivePromptHistory` are built in
   [src/quality-check/orchestrator.ts:75](../../src/quality-check/orchestrator.ts#L75)
   and returned to Process #2 — but never written to DB and never
   included in `TurnTrace`
   ([src/shared/trace/index.ts:14](../../src/shared/trace/index.ts#L14)).
   So "which check fails most often" cannot be answered from existing
   data; only by re-running with new instrumentation, or by local repro
   (this report uses local repro for cosines).

## Method

Read-only DB pull via [scripts/inspect-fallback-turns.ts](../../scripts/inspect-fallback-turns.ts)
against production `DATABASE_URL` (Supabase eu-central-1 transaction
pool). Run on 2026-05-06.

- Pulled the last 100 `turns` rows + qaOutcome distribution over last 200
- Pulled all `library_versions` rows (active + inactive, all libraries)
- Computed Voyage cosine for every non-null `responseText` against a
  fresh centroid built from the **current seed**'s `voiceRulesV1.rules[*].positiveExamples`
- Computed canonical hashes of the current seed files for both
  libraries

The output JSON contains PII (`userMessage`, `responseText`) and is
**not** committed; it lives at the local diagnostic path. This report
quotes only IDs (8-char prefix) and aggregate numbers.

## Finding 1 — Library promotion mismatch (root-cause hypothesis)

| Library          | Seed hash (current) | DB active hash | Match? |
| ---------------- | ------------------- | -------------- | ------ |
| voice_rules      | `f1077420458e…`     | `8bcd22a03b9c…`| ❌     |
| cultural_framing | `93f35de917fb…`     | `d9695618742c…`| ❌     |

Both DB rows show `version=v1`, `publishedAt=2026-05-04T16:01:1[2,4]Z`,
`publishedBy=hamse@hogaan-team:signed-off-2026-05-04`. The Phase 12
audit-mitigation commits (`cd0e01b` R3 voice rules, `e72844a` R7-9
cultural framing affinity, `e76385b` cultural framing v2 with Xil)
landed AFTER 2026-05-04 — modifying the seed files in code without
inserting new `library_versions` rows.

There is precedent for the publish step: [scripts/publish-crisis-resources-v2.ts](../../scripts/publish-crisis-resources-v2.ts)
exists and DID insert `crisis_resources v2` (visible as `active=true`
in DB). No equivalent publish script was added for voice_rules or
cultural_framing.

Per [src/libraries/publish.ts:64-69](../../src/libraries/publish.ts#L64-L69),
calling `publishLibraryVersion(db, {libraryName: 'voice_rules', version: 'v1', payload: voiceRulesV1, ...})`
in production right now would FAIL with "v1 exists with different
content — bump version" — confirming the divergence between seed
content and stored payload.

**Operational impact at request time:**

- Process #2 §10 calls `getActiveLibraryVersions(deps.db)` and passes
  the resolved libraries into prompt assembly and the QC orchestrator.
  Prompt-assembly uses `voiceRules.payload` from the DB row → OLD
  content.
- [src/quality-check/voice-consistency.ts:1](../../src/quality-check/voice-consistency.ts#L1)
  imports `voiceRulesV1` directly from the seed file → NEW content.
- Centroid is built from NEW `positiveExamples`. Candidate text is
  generated by Haiku conditioned on OLD voice-rules content. Cosine
  comparison is between two different versions of "Hamse voice."

This is consistent with the cosine evidence in Finding 3 below: real
Haiku responses cluster 0.655–0.681 — narrowly above the 0.65
threshold, with margins as small as 0.005. A small shift in centroid
direction (which a content change like adding Rule 11 / rewriting
Rule 10 produces) is enough to drag a fraction of turns under the
threshold.

**The user-reported "~50% fallback rate on T1/T4 max-retries, T7/T8
degraded" doesn't appear here.** Hypotheses for the source mismatch:

- T1/T4/T7/T8 are tier names from the audit-evidence schema
  ([src/shared/audit-evidence/types.ts](../../src/shared/audit-evidence/types.ts) — tier T1..T5).
  The user may be reading from a synthetic test cohort under
  `tests/coaching/*` or `tests/quality-check/*`, not the prod `turns`
  table.
- The fallback rate may be from a profile-latency or BPMN-coverage run.
- Production volume is too low (5 real coaching turns visible) to
  compute a stable rate; the failure rate may be real but under-sampled
  here. Recommend the user share the data source they're observing.

That said: 1 E3 in 5 real turns is **20%**, and the failing turn's
userMessage is a literal "hi" Greeting — high concern even at low
volume. We don't have the failing candidates (not persisted) so we
can't say which check rejected them.

## Finding 3 — Voice cosine clusters at threshold

Real Haiku turns (n=4, excluding the E3 fallback template):

```
0.655  ┃▎  E2 retry=1
0.664  ┃▌  E2 retry=2
0.681  ┃▊  E2 retry=1
       │
0.65   ┕━ threshold
       │
0.561  ┃   E1 — Llama fast-model (qa passed; voice check likely
                skipped on this path or service_unavailable;
                cannot verify without per-check persistence)
```

- Mean: 0.633. Median: 0.660.
- 3/4 Haiku turns sit 0.005–0.031 above the 0.65 cutoff.
- The user's hypothesis "if scores cluster 0.55–0.65, threshold is
  too tight" is **directionally confirmed**: Haiku-passing cosines
  cluster 0.65–0.68 (just above), with margins so small that any
  centroid drift would push a fraction of turns under.
- Combined with Finding 1, the centroid IS drifting — built from new
  `positiveExamples` while Haiku is conditioned on old voice rules.

Note: n=4 is too few for a real distribution. The directional signal
is consistent with the live-system regen rate (E2 = 63.5% on the last
200 rows including synthetic data, but 3/4 = 75% on the real Haiku
sample).

## Finding 4 — R10 invalidation hook is wired but has a static-import gap

The R10 fix [src/libraries/resolver.ts:163-175](../../src/libraries/resolver.ts#L163-L175)
correctly calls `invalidateVoiceCentroidCache()` from
`invalidateLibraryCache()` via lazy import. The hook would fire
correctly on a future `publishLibraryVersion(...)` call.

**Gap:** [src/quality-check/voice-consistency.ts:1](../../src/quality-check/voice-consistency.ts#L1)
imports `voiceRulesV1` statically. Even if a v2 row were published
in DB and `invalidateLibraryCache()` cleared the centroid cache, the
recomputation would still use the same `voiceRulesV1` symbol the
process loaded at module init. Process restart is required to pick
up new seed content.

This is moot today because no v2 has been published to DB. It becomes
real the moment a publish script runs.

## What we can't answer from this data

- "Which check IDs are appearing as soft_fail / hard_fail / service_unavailable":
  per-check status is in `qc.checks[]`, returned from `runQualityCheck`
  but not persisted. The TurnTrace shape ingested by Axiom does not
  include `checks[]` or `correctivePromptHistory` — verified at
  [src/shared/trace/index.ts:14-35](../../src/shared/trace/index.ts#L14-L35)
  and [src/coaching/orchestrator.ts:402-428](../../src/coaching/orchestrator.ts#L402-L428).
  Recovering this requires either new instrumentation or controlled
  local replay.

- "Log the LLM's reasoning text on failures (useful-to-society,
  tangible-action)": the LLM checks already emit reasoning into the
  `reason` field
  ([checks-llm.ts:264-321](../../src/quality-check/checks-llm.ts#L264-L321)),
  but the field is discarded with the rest of `checks[]`. Same fix
  unblocks both.

- "Why the Llama 0.561 turn passed despite cosine below threshold":
  voice-consistency may have returned `service_unavailable` (treated
  as skip) on the fast-model path, or the live centroid differed from
  the one we computed here. Cannot disambiguate without per-check
  persistence.

## Hypotheses, ranked

1. **(Most likely)** Library content drift between DB and seed is the
   primary driver of high E2 regen rate. Voice-consistency's centroid
   moved when Phase 12 R3 ratified Rule 11 / rewrote Rule 10; Haiku is
   still steered by old voice rules in the system prompt. The threshold
   is fine; the conditioning is split. **Test:** publish current seeds
   as `v2`, deploy, observe E2 rate drop on next 50–100 real turns.

2. **(Plausible)** Threshold 0.65 is genuinely tight even at content
   parity. n=4 is not enough to call this; would need ≥30 real turns
   post-fix to evaluate.

3. **(Possible, separate problem)** The user's reported ~50% rate is
   from a synthetic test harness rather than the live `turns` table.
   The two digits should be reconciled before retuning thresholds.

4. **(Independent finding)** R10 static-import gap means even a clean
   v2 publish won't fully take effect without a Render restart. Mitigate
   when a publish script is run.

  for every future incident.
- **Defer threshold change.** Don't lower 0.65 until Findings 1 + 3
  can be re-measured against parity-aligned content.
- **Investigate the E3 Greeting turn (`97a0d5e7`).** userMessage is
  "hi"; 3 attempts couldn't pass. Even with no per-check data, this
  warrants a short manual inspection of the regen prompts assembled for
  short Greetings.
